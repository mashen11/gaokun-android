# 手写笔（华为 M-Pencil）—— 在一块只认幅度的面板上把笔做出来

> 内核补丁：`patches/0078`–`0082`（树外维护，已登记进 `scripts/kernel-apply-patches.sh`）。
> 测量/判定工具：`scripts/touch/`（`check-pen-android.sh`、`pen-ghost-ab.sh`、
> `pen-multitouch-analyze.py`、`pen-line-analyze.py`）。
> 下面所有数字都是在 gaokun3 这台机器上量出来的。

---

## 0 一句话

这块面板（Himax HX83121A）的触点**不是 IC 固件给的**，是内核驱动自己从 40×60
原始电容网格上跑一条流水线算出来的：

    去基线 → CMF 共模 → IIR → BFS 连通域 → 掌压 → 峰值 → 三道过滤 → 质心 → 跟踪

而**这条流水线只认幅度**。指腹过得了它的闸门，笔过不了。所以"支持手写笔"在这台机器上
不是"加一段协议解析"，而是**在 raw 网格上另开一条与手指并行的通路**。

---

## 1 为什么笔在原有的流水线上必然失败

2026-09-30 的四阶段实测（原始盘上重量的）：

| | 核心尺寸 | 峰值 | 备注 |
|---|---|---|---|
| **笔尖接触** | 2×2 格 | **492** | 裙边只有 40~80 |
| **静息噪声** | — | σ ≈ 34（单帧最大 120）| >150 的像素：**0 个** |
| **指腹对照** | 4×5 格 | 3836 | >150 的像素：4399 个 |

而出厂闸门是 `peak_threshold = 800`。**800 > 492 ⇒ 笔尖连一个连通域都种不出来**，
流水线在后面每一级看到的都是"零事件"。这也是为什么"放宽闸门"看起来像显然的解法。

**放宽闸门这条路已经用实测量过、判死：** 把驱动那条流水线逐行复刻成 Python
（`docs` 侧保留的 `hx-algo-replay.py`），先复刻出厂行为、再扫参数。结论是
**把闸门放宽到够收下笔尖，噪声也一起进了连通域** —— 面板上的量化噪声不再是
"离阈值 11 倍"的安全边距，而是直接产出幻影触点。两个目标（收下 492 的峰、挡住 120 的噪声）
在同一个幅度判据下不可兼得。

⇒ 于是笔另走一条路。

---

## 2 笔的独立通路（`patches/0078`）

* 直接在 `raw_frame` 上按半格步长滑窗取局部峰值当候选，**不经过 `macro_threshold`**；
* 候选过一道独立的笔阈值，喂进一条**与手指分离**的轨迹；
* 位置细化为**格内加权质心**（`pen_centroid_win`，默认 2；写 0 = 逐字复现 argmax-only）。
  动机是**量化**不是手抖：一格 = 42.67 单位 ≈ 4.27 mm，argmax 的量化下界是 ±0.5 格 ≈ 2.13 mm。
  质心**钳在 argmax 所在格内**（细化，不是搬家）—— 否则面板别处一个宽的矮包
  （搁着的手、充电器耦合）能把质心拖离笔尖。
* 轨迹闸门仍建在 **argmax** 上：那个量的连续性是被实测过的，换成平滑位置会让阈值失去意义。
* `debugfs/stack_raw` 的导出上限做成可调（原来是死代码 `dump_frame()`），便于整帧取证。

**默认关**（要 `echo 1 > algo/pen_enabled`）—— 这是当时为了能安全上机做灰度留的，
到 0080 才改成默认开。

## 3 触点判据：幽灵剔除与点击响应（`patches/0079`）

有了通路之后，接下来是"别把不是笔的收进来、真的点一下要立刻响应"。
这两件事动的是同一段 latch 逻辑，拆不开。

### 3.1 幽灵剔除：凡是不靠"动了"证明自己的 latch，都要过空间判据

`by_hold`（连续 30 帧就认）是三条 latch 路里**唯一没有空间判据**的一条。实测
（画 2 条线 + 快点 5 下）：14 个 latch 段里 12 段是真动作（幅度路、`nbr8` 高），
2 段是 `by_hold` 收的**静止偏移**（`travel=0`、`nbr8` 只有 ~300、贴底边），
而被拒的 9 段里有 7 段也在同一格。另一个方向也成立：**出生后位移不涨却一直报的候选不是笔**
（行程判据）。

写成规则而不是特例：

```c
	bool spatial_ok = algo->pen_min_nbr8 <= 0 ||
			  pen->nbr8_streak >= algo->pen_min_nbr8;
	bool by_amp  = ... && spatial_ok;
	bool by_hold = ... && spatial_ok;
```

### 3.2 "点一下"立刻响应：时间维用尽之后换幅度维

时间维的 latch（`by_hold`）最快也要 30 帧才响应一次点击，手感必然黏。
给点击单开一道**幅度闸门**：一笔之内同格候选的峰值**一整段取最大**，过 `pen_tap_level` 即认。
并把空间判据（邻域闸门 `nbr8`）**只归点击那条路** —— 划动本来就靠"动"自证，
再叠邻域门只会把快速笔划切碎。

### 3.3 四个质心窗口吃同一帧

原先四个方向的窗口各自取帧，于是"手"在一次读数里变成了变量。统一到同一帧。

## 4 系统集成（`patches/0080`）

* **申报 `ABS_MT_TOOL_TYPE`**，在笔轨迹上逐帧报 `MT_TOOL_PEN`。
  这是用户态区分手指与笔的**唯一**依据 —— 画线应用据此切压感/倾斜/笔刷。
  此前驱动一个 `MT_TOOL_*` 都没报，笔在应用眼里就是一根奇怪的粗手指。
  ⚠️ `touch.deviceType = stylus` 是无效值（合法取值只有 touchScreen / touchPad /
  pointer / default），`.idc` 对"这是不是笔"没有任何影响。
* **轨迹按工具隔离**：笔与手指共用一套轨迹索引会互相顶掉（落笔瞬间手指轨迹被挤掉、
  抬笔又被抢回来，表现为"笔一动手指就断"）。按 `is_pen` 分开记账、各自分配 slot。
* **笔通路改默认开**：判据到这里齐了，"拿起笔"不该需要先写一个 sysfs 文件。
  `algo/pen_enabled` 旋钮保留，仍可运行时关。
* 顺带修一处计数卫生：`stats_store` 清零时漏掉 pen 的计数，于是"清空统计"之后旧值还在。

## 5 边缘补偿、可观测性、镜像去重（`patches/0081`）

* **边缘点击**：邻域闸门数的是"邻域里够亮的格子数"，在面板边缘天然吃亏 ——
  屏幕外那半圈格子不存在，同一个笔尖在边上比中间少一半邻居。按格子到边缘的距离做
  几何查表补偿。补偿之后原先为迁就边缘而抬高的幅度门可以收回：`pen_tap_level` **198 → 160**。
* **可观测性**：记录 streak 峰值与每一帧的 `frame_flags`（被哪道闸门拒了），
  "点了没反应"从此是一次 `cat` 的事。
* **单点镜像去重**：采样率到 120 Hz 之后，同一物理接触会在相邻帧被识别两次，
  上报成两个紧挨着的触点 ⇒ 用户态判成 pinch。给笔轨迹一个身份标识，
  同一身份在滑动窗口内只保留一个上报。

## 6 幽灵触点：「一指变两指」（`patches/0082`）

**症状**：单指操作偶尔被判成两指 —— 画线断、页面莫名缩放。

**根因是出生条件的 bug，不是阈值。** 笔的通路只在一帧里"振幅通路本帧没有任何连通域"
（`cnt == 0`）时才被问一次。可 **"0 contact" ≠ "没手指"**：一个匹配失败的 finger 轨道
仍在 `track_lost_frames` 的宽限期里 `active`，坐标冻结、继续上报。而笔的出生判据比
"手指还在"更松 ⇒ 它把**同一个 finger blob** 收编成了笔 ⇒ 同一帧里出现两个指针
（`FINGER` + `PEN`）⇒ 用户态判成 pinch。

**判据（可证伪）：** 把 evdev 流逐帧摊开，取所有「同帧 ≥2 个 live slot 且几何距离 < 60 px」
的帧，工具组合**清一色是 `{finger, pen}`，从没出现过 `{finger, finger}`**。
后者才是真的两指。

**修复**：`hx_pen_scan()` 在 latch 之前先看 `tracks[]` ——
只要还有 `active && !is_pen` 的轨道，就拒绝新建笔轨道。新增观测 `pen_dec_finger`
记录"因为手指还活着被拒"的次数。

> ⚠️ 与 `pen_min_nbr8` **无关**（把 nbr8 提到 150 该出的照样出）——
> 它修的是**出生条件**，不是**出生阈值**。修复前为了压住这个症状把 `pen_min_nbr8`
> 抬到 367 是权宜；修复之后回 150 即可。

## 7 已判死的路（别再走一遍）

| 想法 | 为什么不行 |
|---|---|
| 放宽 `macro_threshold` / `peak_threshold` 让笔尖进来 | 噪声一起进连通域，幻影触点。§1 有实测 |
| 用 `pen_smoothing`（基于速度预测的 IIR）补点 | 它是**滞后不是插值**：实现是 `x=(3·旧+新)/4`，加 ~25 ms 延迟、**不改点间距** |
| 把笔报告当成"连续压感"的来源去移植 | Windows 侧的笔报告描述符里**压感只占 1 bit**（悬停 Z 也只 1 bit）。这一代笔在 HID 层就没有连续压感，没有字段可移植 |
| "画线呈点状/不连续"当成驱动问题 | 手指与笔的采样率**同源（120 Hz，gesture 级实测 8.32 vs 8.34 ms）**。系统侧已到 TDDI 同步的上限，驱动 53 个属性里没有 rate 旋钮。是否插值由**绘图 App** 决定（常见的绘图 App 不插值）—— 只能在 App 侧解决 |

## 8 怎么验证

三层，从"认不认"到"有没有幽灵"到"笔划质量"：

```sh
# ① Android 到底认不认这支笔（推到设备上跑；期间用笔划两下）
adb push scripts/touch/check-pen-android.sh /data/local/tmp/
adb shell su -c 'sh /data/local/tmp/check-pen-android.sh --capture 8'

# ② 纯手指手势下有没有幽灵（笔放远；主机一条命令）
DEVHOST=<serial> bash scripts/touch/pen-ghost-ab.sh 60 "nbr8=150"

# ③ 笔划质量（采样率 / 每帧步长 / 位移为 0 的帧占比）
python3 scripts/touch/pen-line-analyze.py <capture.txt> --cols 60 --xmax 1599
```

判据：

* **①** 三层全过（`dumpsys input` 的设备 `Sources:` 含 `SOURCE_STYLUS`、
  节点有 `ABS_MT_TOOL_TYPE` 能力位、实抓事件里出现 `MT_TOOL_PEN`）
  ⇒ 应用里 `MotionEvent.getToolType() == TOOL_TYPE_STYLUS`。
* **②** 笔放远做纯手指手势：`slots_born_pen ≈ 0`，且 evdev 里「同帧两点 <60 px」的帧 ≈ 0。
  有幽灵时指纹是 `slots_born_pen` 非 0，且那些帧的组合是 `finger/pen`。
* **③** 笔与手指的帧间隔中位数都应在 8.3 ms 附近（≈120 Hz）。

## 9 已知限制

* **压感**：这一代笔经 HID 上报的压感只有 1 bit（见 §7）。有笔压感的绘图 App
  在这台机器上只能拿到"下笔/未下笔"，拿不到笔压曲线。这是硬件/固件层面的，
  不是驱动能补的。
* **悬停（hover）**：evdev 层在"悬而未触"时**零事件**（连一帧都没有），
  所以应用侧拿不到悬停。同样不是驱动层能修。
* **笔的画线密度**：受限于 120 Hz 采样与 App 是否插值（见 §7）。
